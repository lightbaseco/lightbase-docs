---

<Note>Infrastructure support is optional.</Note>
<Info>
  This feature is in development.\
  Reach out to your Lightbase contact to have it enabled for evaluation.
</Info>

Lightbase can index your cloud infrastructure, adding it to the context it already has about your organization and raising the level of detail in the model it builds of your system. Connecting your infrastructure is useful in several ways:

- Lightbase answers questions that are purely about infrastructure, in chat or through the MCP server:

  <Card title="Example questions">
    - Which API Gateway endpoints are backed by this Lambda function?
    - Which buckets are publicly accessible?
    - Which roles can read from the `customer-data` table?
    - Is the payments API reachable from the internet, or only from inside the VPC?
  </Card>

- Lightbase relates each application to the infrastructure it runs on, down to the instance, container, or function serving it. That knowledge lets Lightbase anticipate problems before they cause an incident, and troubleshoot failures where the cause isn't only the code: an application hitting a scaling limit, a misconfigured gateway stopping requests, a service account missing a permission it needs at runtime, or a security group blocking a connection the code expects to make.
- Lightbase resolves the connections it already finds more precisely. Connections between parts of your code, and between applications across your organization, come from the code alone. Some of the detail behind them sits in environment variables, and those values only exist in your infrastructure. Reading them there turns a reference Lightbase can't resolve from the code into the actual resource it points to.
- Lightbase indexes serverless function code that isn't versioned in your repositories. When a function's source only exists in your cloud account, Lightbase reads it from the function itself. It lands in the model alongside the rest of your code. That covers functions edited directly in the console and functions deployed from outside version control.

## Cloud providers

<Note>
  Lightbase currently supports AWS. Support for additional cloud providers is planned.
</Note>

### AWS

#### Setup

To analyze your infrastructure, Lightbase needs read-only visibility into your AWS account. You grant access through an AWS CloudFormation stack. Lightbase gives you a direct link to the Quick create stack page in the AWS console, with the template and its parameters already filled in, so there's nothing to download or upload yourself.

<Info>
  Permissions are strictly read-only. Lightbase only ever calls `Describe`, `List`, and `Get` operations, and never creates, modifies, or deletes anything in your account. For AWS Secrets Manager specifically, Lightbase reads metadata such as name and rotation configuration, never the secret value itself.
</Info>

There are two ways to connect, depending on whether you use AWS Organizations:

- **Organization account**: connect your organization's management account, then choose which member accounts to grant access to.
- **Individual account**: connect a single AWS account. Use this if you don't use AWS Organizations, or only want to give Lightbase access to one account.

The values shown below are examples. Use the ones your own setup link and templates provide.

<Tabs>
  <Tab title="Organization account">
    <Steps>
      <Step title="Create IAM resources">
        Sign in to your organization's management account, then open the setup link Lightbase gives you. It takes you straight to the Quick create stack page:

        ```text
        Stack name: LightbaseAccess
        LightbaseTenantRoleArn: arn:aws:iam::123456789012:role/lightbase-scanner-role
        ExternalId: aB3dE7fG9hJ2kL4mN6pQ8rS1t
        ```

        Review the parameters without changing them. Acknowledge that the stack creates IAM resources with custom names, then create the stack. It creates a dedicated IAM role, `LightbaseOrgDiscovery`, trusted only by Lightbase and scoped to read-only access.

        Where in AWS: [CloudFormation stacks](https://console.aws.amazon.com/cloudformation/home#/stacks)
      </Step>
      <Step title="Activate the connection">
        Once the stack finishes, copy the role ARN from its outputs and share it with your Lightbase contact to activate the connection.
      </Step>
      <Step title="Grant access to member accounts">
        Deploy the second template as a CloudFormation StackSet from the management account. Unlike the first template, this one isn't a pre-filled link: create a new StackSet, select the template, and enter its parameters:

        ```text
        LightbaseTenantRoleArn: arn:aws:iam::123456789012:role/lightbase-scanner-role
        ExternalId: aB3dE7fG9hJ2kL4mN6pQ8rS1t
        ```

        Name the StackSet yourself, then choose which accounts to target: your whole organization, specific organizational units, or individual accounts.

        Where in AWS: [CloudFormation StackSets](https://console.aws.amazon.com/cloudformation/home#/stacksets)
      </Step>
    </Steps>

  </Tab>

  The stack reaches `CREATE_COMPLETE` and the new role appears in IAM. Lightbase confirms the connection once it can assume the role.
</Check>

#### What Lightbase discovers

Lightbase catalogs your AWS resources by service. The groups below cover the services that shape the model of your system. Each one names the resources Lightbase reads, and what they add to that model.

<AccordionGroup>
  <Accordion title="Compute (EC2)" description="Instances, volumes, and network interfaces.">
    EC2 instances are where Lightbase anchors an application to the machine that runs it. That link tells you which applications share a host, which volumes they depend on, and which network interfaces carry their traffic. When you are diagnosing a failure the code does not explain, it gives you the host to look at.
  </Accordion>
  <Accordion title="Networking" description="VPCs, subnets, route tables, network ACLs, internet and NAT gateways, VPC endpoints, and elastic IPs.">
    Networking is what tells Lightbase how much of your system each application can see. Lightbase places every resource in its VPC and subnet, and records the security groups protecting it. From there you can tell whether an application is reachable from the internet, or only from inside the VPC. Route tables, network ACLs, gateways, and VPC endpoints describe how a connection leaves your network, which is what you check when the code expects a connection that never happens.
  </Accordion>
  <Accordion title="Load balancing" description="Load balancers (ALB, NLB, and Gateway) and target groups.">
    Load balancers are the front door of an application. Target groups tell Lightbase which instances or functions sit behind a listener, so a route in your code connects to the hostname callers actually use. They also show how one application spreads across targets, and where public traffic enters your account.
  </Accordion>
  <Accordion title="Auto Scaling" description="Auto Scaling groups.">
    Auto Scaling groups give the capacity range an application runs within. Reading them tells you the ceiling an application hits under load, so you can trace an incident back to a scaling limit.
  </Accordion>
  <Accordion title="Storage" description="S3 buckets.">
    Buckets hold data your flows depend on, and the bucket's configuration decides what you can do with that data. Lightbase resolves which applications read and write each bucket, and reads its access, exposure, and retention configuration alongside them. That tells you who can reach the data, whether it is reachable from the internet, and how long it stays there. Retention is what tells you whether an invoice written last quarter is still in the bucket.
  </Accordion>
  <Accordion title="Serverless" description="Lambda functions.">
    Lambda functions often hold code that never reaches a repository, because someone edited it in the console or deployed it from outside version control. Lightbase reads the source from the function itself and indexes it with the rest of your code, so a flow that passes through the function keeps going. It also reads the function's configuration and environment variables, which resolve the resources the function talks to.
  </Accordion>
  <Accordion title="Databases" description="DynamoDB tables.">
    Tables in your cloud account are the source of truth for your data layer, and code is a partial description of it. Reading the tables directly gives Lightbase the keys and indexes your queries rely on, which raises the precision of your [curated schema](/data-curation/databases). Lightbase also resolves which roles and applications can reach each table, so the access your code implies is confirmed against the permissions that exist.
  </Accordion>
  <Accordion title="Messaging" description="SQS queues.">
    Queues are where cross-application flows usually break, because a producer and a consumer rarely spell a queue the same way. Reading the queues in your account gives Lightbase the real queue, so both ends of a flow attach to the same one. It also brings in each queue's own configuration, and the applications permitted to send to it or receive from it.
  </Accordion>
  <Accordion title="Identity and access (IAM)" description="Users, roles, and groups.">
    IAM decides what your code is allowed to do at runtime. Lightbase parses policies, both inline and attached, to resolve which users and roles reach which resources, and which roles they can assume. That turns an intended access into a confirmed one: your application calls `PutObject` on a bucket, and the role it runs under either allows the call or does not. Lightbase also flags users, roles, and groups whose policies grant full administrator access, so you can find them when you query your infrastructure.
  </Accordion>
  <Accordion title="Secrets" description="Secrets Manager entries, metadata only.">
    Applications reach their databases and their counterparties through credentials they read at runtime. Lightbase links the code that reads a secret to the entry behind it, using metadata such as its name and rotation configuration, never the value.
  </Accordion>
  <Accordion title="DNS and domains" description="Route 53 hosted zones and registered domains.">
    Hosted zones hold the names your system answers to. Lightbase resolves a hostname, whether it appears in a client's HTTP call or in an application's configuration, to the resource that serves it. For an application reachable from the internet, this is how you get the real domain in front of it instead of a load balancer's generated name.
  </Accordion>
  <Accordion title="APIs" description="API Gateway REST and HTTP APIs.">
    An API Gateway API defines an application's routes outside its code. Lightbase maps each route to the function or application behind it, so an [entrypoint](/architecture/entrypoints) found in a Lambda function connects to the path and method callers use. It also shows which routes are exposed, and under which stage.
  </Accordion>
</AccordionGroup>

<Note>
  Resources and their configuration are read exactly, from the AWS APIs. The link between an application and the resource it runs on or reaches is proposed. It depends on resolving names and environment variables, and you can correct it in [data curation](/data-curation/applications).
</Note>
