</Info>

Lightbase can index your cloud infrastructure, adding it to the context it already has about your organization and raising the level of detail in the model it builds of your system. Connecting your infrastructure is useful in several ways:

- **Infrastructure indexing gives your agent visibility of your cloud resources.** For example:

  - Which API Gateway endpoints are backed by this Lambda function?
  - Which buckets are publicly accessible?
  - Which roles can read from the `customer-data` table?
  - Is the payments API reachable from the internet, or only from inside the VPC?

- **Lightbase ties each application to the infrastructure it runs on.** The relationship extends to the instance, container, or function serving it. This context lets agents anticipate problems before they cause an incident and troubleshoot failures where the cause isn't only the code. Examples include:

  - An application hitting a scaling limit
  - A misconfigured gateway stopping requests
  - A service account missing a permission it needs at runtime
  - A security group blocking a connection the code expects to make

- **Infrastructure context adds precision and detail to the connections Lightbase finds in code.** Some of the information behind those connections, such as injected environment variables or the services sitting behind a load balancer, exist only in the infrastructure. Lightbase incorporates this infrastructure context into the model.

## Cloud providers

<Note>
  Lightbase currently supports AWS. Support for additional cloud providers is planned.
</Note>

### AWS

#### Setup

To analyze your infrastructure, Lightbase needs read-only access to your AWS account. The quickest way to get started is through an AWS CloudFormation stack. Lightbase gives you a direct link to the Quick create stack page in the AWS console, with the template and its parameters already filled in, so there's nothing to download or upload yourself.

<Info>
  Permissions are strictly read-only. Lightbase only ever calls `Describe`, `List`, and `Get` operations, and never creates, modifies, or deletes anything in your account. For AWS Secrets Manager specifically, Lightbase reads metadata such as name and rotation configuration, never the secret value itself.
</Info>

There are two ways to connect, depending on whether you use AWS Organizations:

- **Organization account**: connect your organization's management account, then choose which member accounts to grant access to.
- **Individual account**: connect a single AWS account at a time. Use this if you don't use AWS Organizations, or only want to give Lightbase access to one account.

The values shown below are examples. Use the ones your own setup link and templates provide.

#### What Lightbase discovers

Lightbase catalogs your AWS resources by service. The groups below cover the services that shape the model of your system. Each one names the resources Lightbase reads, and what they add to that model.

<AccordionGroup>
  <Accordion title="Compute (EC2)" description="Instances, volumes, and network interfaces.">
    EC2 instances run applications on virtual machines, with volumes for block storage and network interfaces for VPC connectivity.

    Lightbase links each application to the instance that runs it. It records shared hosts, attached volumes, and network interfaces. These relationships identify the compute, storage, and network resources involved in failures that are not visible in the code.
  </Accordion>
  <Accordion title="Networking" description="VPCs, subnets, security groups, and gateways.">
    VPCs and subnets define network boundaries, while security groups, route tables, and gateways control which resources can communicate and where traffic can go.

    Lightbase places resources in their VPCs and subnets and records the security groups that protect them. It uses routes, network ACLs, gateways, and VPC endpoints to determine whether an application is internet-facing and reconstruct how expected connections traverse the network.
  </Accordion>
  <Accordion title="Load balancing" description="Load balancers (ALB, NLB, and Gateway) and target groups.">
    Load balancers accept traffic on listeners and distribute it across instances or functions registered in target groups.

    Lightbase maps listeners and target groups to the applications behind them. These relationships connect code routes to the hostnames callers use, show how an application is distributed across targets, and identify where public traffic enters the account.
  </Accordion>
  <Accordion title="Auto Scaling" description="Auto Scaling groups.">
    Auto Scaling groups maintain a configured number of EC2 instances and adjust capacity within minimum and maximum limits.

    Lightbase relates those limits to the applications running in the group. It uses the maximum capacity to identify scaling ceilings that can explain failures under load.
  </Accordion>
  <Accordion title="Storage" description="S3 buckets.">
    S3 buckets store objects used by code flows. Bucket policies and configuration control access, public exposure, and retention.

    Lightbase resolves which applications read from and write to each bucket. It records access, exposure, and retention settings alongside those relationships. This shows who can reach the data, whether it is internet-accessible, and how long stored objects remain available.
  </Accordion>
  <Accordion title="Serverless" description="Lambda functions.">
    Lambda functions run code in response to events without a persistent server. AWS stores their deployed source and runtime configuration.

    Lightbase reads deployed source code that is not available in connected repositories and adds it to the model. It also maps each function to its surrounding infrastructure. Lightbase records which resources and services can invoke the function, which resources the function can access, and the permissions behind those relationships.
  </Accordion>
  <Accordion title="Databases" description="DynamoDB tables.">
    DynamoDB tables store items under partition and optional sort keys. Secondary indexes support additional query patterns.

    Lightbase uses database metadata to represent the data layer more precisely in the model.
  </Accordion>
  <Accordion title="Messaging" description="SQS queues.">
    SQS queues buffer messages between producers and consumers, allowing applications to exchange work asynchronously.

    Lightbase uses queue metadata to represent asynchronous communication between applications more precisely in the model.
  </Accordion>
  <Accordion title="Identity and access (IAM)" description="Users, roles, and groups.">
    IAM users, roles, and groups define identities in an AWS account. Attached and inline policies control which actions those identities can perform on resources.

    Lightbase parses both policy types to resolve which users and roles can access each resource and which roles they can assume. It compares those permissions with operations found in code, such as `PutObject` on an S3 bucket. Lightbase also identifies users, roles, and groups with full administrator access.
  </Accordion>
  <Accordion title="DNS and domains" description="Route 53 hosted zones and registered domains.">
    Route 53 hosted zones contain the DNS records that route traffic for a domain. Registered domains identify the internet names managed through the account.

    Lightbase resolves hostnames from HTTP calls and application configuration to the resources that serve them. For internet-facing applications, this connects generated load balancer names to the public domains callers use.
  </Accordion>
  <Accordion title="APIs" description="API Gateway REST and HTTP APIs.">
    API Gateway REST and HTTP APIs expose routes that forward requests to integrations such as Lambda functions and application backends.

    Lightbase maps each gateway route to the function or application behind it. This connects an [entrypoint](/indexing/indexer) found in code to the path, method, and stage used by callers. Lightbase also records which routes are exposed.
  </Accordion>
</AccordionGroup>
