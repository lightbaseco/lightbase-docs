A **counterparty** is something outside your system that your code interacts with: a cloud service, a payment provider, a partner API, a SaaS tool you pay for. Lightbase detects them as it traces your flows and records what kind of interaction it found. In **Counterparties** you rename them, describe what each interaction is for, and organize them into the groups your company actually thinks in.

Those groupings are commercial and organizational facts, not technical ones. Nothing in your code says that three endpoints belong to one vendor contract, so this is where you say it.

## Counterparty groups

A **counterparty group** represents one external entity your company deals with. Groups come in two kinds.

<CardGroup cols={2}>
  <Card title="Technical" icon="cloud">
    Infrastructure and platforms, for example `AWS`.
  </Card>
  <Card title="Business" icon="briefcase">
    Suppliers, contracted SaaS, clients, or any commercial relationship.
  </Card>
</CardGroup>

A counterparty can belong to several groups at once, which is what makes the model match reality: a payments endpoint can sit in the group for that specific vendor *and* in the group you use to track everything that processes cardholder data.

## What you can edit

| Object             | You curate                          | Lightbase provides                     |
| ------------------ | ----------------------------------- | -------------------------------------- |
| Counterparty       | Name, description, group membership | The interaction type found in code     |
| Counterparty group | Name, kind (technical or business)  | The group itself, built from your code  |

<Info>
  The interaction type stays as detected. It is evidence from your code, so Lightbase shows it but never overwrites it.
</Info>

## Why teams care about this

* **A third-party inventory tied to real code.** Not a spreadsheet someone maintained once, but the vendors your flows actually reach.
* **Vendor and compliance reviews with evidence.** Answer which flows send data to a given provider, and which [applications](/data-curation/applications) break if you drop them.
* **Naming variants consolidated.** Five clients pointing at the same vendor stop looking like five vendors.
* **A clear system boundary.** The line between your software and everyone else's becomes explicit.
