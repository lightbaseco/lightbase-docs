Your agent works with the context of the repository you have open. However, Lightbase has indexed every repository in your organization and built one model of your system. That model holds every relationship between your services, [databases](/data-curation/databases), [business entities](/core-concepts/business-entities), and [counterparties](/core-concepts/counterparties).

To give your agent that context, Lightbase exposes an MCP server. You keep describing your task to your agent the way you do now. The agent decides when the open repository doesn't hold the answer and calls Lightbase. It gets that context back and keeps working.

Some examples of when your agent could call Lightbase:

- If your agent needs the purpose behind the code it's reading, it can call Lightbase for the context the file doesn't hold. That adds the use case the code belongs to, the code flow it's part of, who calls into it, and the outputs it produces. Your agent keeps working without altering what that code is there to do.
- If your agent is about to change a resource other services share, it can call Lightbase first. The resource might be a bucket, an SQS queue, or the response shape of an HTTP handler, among others. Lightbase returns every other service that reads or writes it, so your agent can tell you which contracts the edit would break.
- If your agent is debugging an error whose cause sits outside the repository, it can call Lightbase for the causes it can't see. For example: a role missing a permission, a security group blocking the connection, or an upstream service that changed its response shape. Lightbase points at the one that fits, so your agent applies the right fix.
- If your agent needs the infrastructure behind the code it reads, it can call Lightbase for the answer. For example: the role a function runs under, the queue a producer writes to, or the domain in front of a route.

<Info>
  Roles, security groups, and domains come from your cloud account. [Connect your infrastructure](/indexing/infrastructure) to get them in the answer.
</Info>

## Before you start

You need:

- A Lightbase account with at least one repository connected and indexed.
- An MCP client that supports Streamable HTTP, or one that can run a local bridge like `mcp-remote` for clients that only support local servers.

## Connect to the MCP server

Every MCP client connects to the same Lightbase endpoint:

```
https://mcp.lightbase.co
```

Add the endpoint to your client's configuration. The exact format depends on the client:

<Tabs>
  <Tab title="VS Code">
    Add the server to `.vscode/mcp.json`:

    ```json .vscode/mcp.json
    {
      "servers": {
        "lightbase": {
          "url": "https://mcp.lightbase.co"
        }
      }
    }
    ```
  </Tab>
  <Tab title="Cursor">
    Add the server to `.cursor/mcp.json`:

    ```json .cursor/mcp.json
    {
      "mcpServers": {
        "lightbase": {
          "url": "https://mcp.lightbase.co"
        }
      }
    }
    ```
  </Tab>
  <Tab title="IntelliJ">
    Go to **Settings | Tools | AI Assistant | Model Context Protocol (MCP)**, click **Add**, and paste:

    ```json
    {
      "mcpServers": {
        "lightbase": {
          "url": "https://mcp.lightbase.co"
        }
      }
    }
    ```
  </Tab>
  <Tab title="Claude Code">
    ```bash
    claude mcp add --transport http lightbase https://mcp.lightbase.co
    ```
  </Tab>
  <Tab title="Codex">
    Add the server to `~/.codex/config.toml`:

    ```toml ~/.codex/config.toml
    [mcp_servers.lightbase]
    url = "https://mcp.lightbase.co"
    ```
  </Tab>
</Tabs>

Any other MCP-compatible editor or agent uses the same server URL. Check its own MCP documentation for the exact configuration format.

### Multiple organizations

Your client works with one organization at a time. If you belong to more than one Lightbase organization, add the `org` parameter to the server URL:

```
https://mcp.lightbase.co?org=acme
```

Set it to the organization's slug, the short identifier chosen when it was created. Without the parameter, Lightbase answers from your default organization.

## Authentication

The MCP server uses OAuth 2.1. Each MCP client registers through Dynamic Client Registration, which lets it enroll with the authorization server without manual setup.

The first time the client connects, it opens a browser window. Sign in with the account you already use for Lightbase.

You do not need to generate or add an API key to the client configuration. The OAuth flow manages authentication without storing a long-lived secret there. Lightbase attributes each request to the person who signed in and removes access when they leave the organization.

## Available tools

Lightbase currently exposes a single tool, `query`, which gives your agent all the context described above.
